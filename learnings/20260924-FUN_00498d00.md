# FUN_00498d00 (string.c, `.\strings\stab.str` loader): 78.68% → 100%

## What was wrong

The remaining diff came from two things:

- **Register swap.** The original gives `data_buf` edi and `total` ebx. We had them the other way round, which also reshaped the addressing: the original has `add ebx, eax` in the counting loop, `mov edi, eax` after malloc, and `[edi+ebp]` in the parse loop.
- **Loop and branch shape.** The parse loop was top-tested and not rotated, and the `""` escape used `jne inc; jmp end` polarity.

## Fixes (all pure C)

1. **Declare the initialized scalars first, before the `char token[240] = {0};` array initializer:**
   ```c
   int total = 0;
   int offset = 0;
   char cwd[256];
   char token[240] = {0};
   ```
   The initializer stores now happen before the `rep stos` that zero-fills `token`. That lengthens `total`'s live range, which lowers its allocation priority. MSVC6 weighs use counts against live-range length, so `data_buf` wins edi and `total` falls to ebx. The instructions emitted are the same; only their order and the resulting registers change.
2. **Non-rotated top-tested loop.** Put the fetch in an if/else inside `for (;;)`:
   ```c
   for (;;) {
       if (offset < total) { c = data_buf[offset++]; } else { c = 0; }
       if (c == 0) { break; }
   ```
   A plain `while (offset < total) { c = ...; if (!c) break; }` gets rotated into a bottom-tested loop.
3. **Branch polarity from a redundant else.** `if (c != '"') quote_count++; else c = '"';` compiles to no extra code for the else. It changes the block layout during tail merging, which produces the original's `jne`/`jmp`.

## Things that did NOT move the edi/ebx allocation

- declaration order of uninitialized locals
- variable types (int/unsigned/char*)
- splitting variables into several
- ternary vs if/else fetch
- dead stores
- `__inline` / `static` inline helpers (the allocator sees through the parameter copies; they compile to the same code as writing it inline)
- about 300 randomized surface-form combinations of the loops

What did work: making `total`'s live range longer, or giving `data_buf` more uses. The first fix above is the natural-looking way to do that.

## Method that paid off

Iterating through the full build plus reccmp took about 5 s per variant. A direct single-TU compile with a signature grep took about 1 s:

```sh
./cmake/wrappers/cl /nologo /O2 /c /Isrc/legoland /Itoolchain/msvc6/Include \
    /Fa/tmp/t/fast.asm /Fo/tmp/t/fast.obj $PWD/src/legoland/<copy>.c
awk '/_FUN_00498d00 PROC/,/_FUN_00498d00 ENDP/' /tmp/t/fast.asm > /tmp/t/f.asm
# match signature: add ebx,eax ; mov edi,eax after _malloc ; BYTE PTR [edi+ebp]
```

Check a strict multi-instruction signature, not one register. The early loose checks ("does edi appear after malloc") gave false positives.

## General takeaways

- If the registers are swapped but the instructions match, change live-range length or use counts. Declaration order alone doesn't do it.
- Initializers in declarations (`int x = 0;`) are *not* the same as assignments later on when an aggregate initializer (`= {0}`) sits between them. The position of the store relative to the `rep stos` matters.
- Redundant `else` arms that assign a value the variable already has are a legitimate way to control branch polarity.
