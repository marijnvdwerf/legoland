# RunAppraisal (0x004453a0): Phase 1 analysis

Read-only analysis by 7 parallel analysts (2026-10-08), using tools/frame.py. Slot numbers are entry-relative
(0 = return address). The original function is 0x4453a0..0x44db06 (8085 instructions); reccmp only compares
the first 28728 bytes (our size) because the original size is unknown.

### slot -9172  [scalar]  int
- role: pageStart: index of the first record on the current report page. At every page overflow it is compared with the current block's start index (blockStart, -9120). If they differ, the block restarts on a new page with i = pageStart = blockStart. Otherwise pageStart = i.
- our_variables: iVar3 (decl 1412; 1476 iVar3 = 0; 1520 iVar3 = iVar14; 1553 iVar3 = iVar12; 1957 if (iVar3 == iVar14); 3837 if (iVar3 != iVar14) goto LAB_0044d594)
- evidence: Counts are over the full function (see notes on truncation): 133 writes, 41 reads, never address-taken (no lea or indexed access to any slot in -9172..-9092), one meaning only. Set to 0 at entry, before IsScriptStopped (xor ebp,ebp 0x4453af; mov [esp+0x10],ebp 0x4453b8). In all report blocks the variable lives in ebp: 88x mov ebp,esi and 9x mov ebp,ecx (restart path, e.g. 0x4464bb). Every one of these is followed on its path by a write-through mov [esp+0x10],ebp (92 stores, 0x4453b8..0x44ad09; I checked every def). The compares use the register (cmp ebp,esi 0x445464; cmp ebp,ecx 0x447be3) across rand and GetString calls, and memory is never read in this region. That is impossible for an aggregate member. In the advice loop (head 0x44acbb, back-edge jmp at 0x44d5b3) ebp becomes the record offset from 0x44ad38 on, and pageStart lives only in memory: 40x mov [esp+0x10],esi (0x44ad27..0x44d4ae), 39x cmp [esp+0x10],ecx against blockStart (0x44ae2b..0x44d48a), and 2x mov ebp,[esp+0x10] + cmp (0x44d444, 0x44d574). The restart path at 0x44d59a does mov [esp+0x10],ecx; mov ebp,ecx; jmp 0x44acbb, and the loop head reads ebp as pageStart again (cmp ebp,esi 0x44acf8). This is MSVC6 region allocation: in a register with write-through in some regions, in its memory home in the others.
- ours_differs: Our iVar3 has the same frame slot (-9172) but is never enregistered: 229 memory uses in our build, e.g. 0x41e96f mov eax,[esp+0x10]; cmp eax,ecx. Our build uses ebp as the zero register instead. Our C sets it to 0 after ReadGameButtons (line 1476) instead of at entry. Our C also reuses iVar3 for values that are not pageStart, which the original keeps in eax or in other slots: 4659-4662 (rand result, index temp), 4689 (all-passed loop index; original eax at 0x44dadb-0x44daf4), 4721 (page-search loop index; original eax at 0x44d81c-0x44d845, result in -9096), 4821 (SpeechIsPlaying result). Hypothesis, not tested: making iVar3 a single-purpose pageStart may let MSVC6 give it ebp. That would leave no free callee-saved register for the record offset, which would then spill to the stack as in the original (-9164).

IMPORTANT, ANALYSIS TRUNCATION

- reccmp's database has no original size for RunAppraisal: size(ORIG) = None, recomp_size = 28728.
- permuter_out/.orig_symbols.json stores any_size() = 28728, which is OUR function's size (ends 0x41e820+0x7038). So frame.py decodes the original only up to 0x44c3d8: 6667 instructions, and the only ret it sees is the early return.
- The real function ends with the ret at 0x44db05: 8085 instructions, jump table at 0x44db08, next symbol at 0x44db40. Its size is 0x87a0 = 34720 bytes, against our 28728.
- reccmp's compare_function reads min(orig_max, recomp_size) = 28728 bytes of the original. So the match % never sees the original's last ~6000 bytes: advice categories 0x18000/0x260000/0x1080000/0xc00000, the n==0 test, the final row, the whole display/interaction loop and the epilogue.
- Consequences for the brief:
  - Slot counts exclude that tail. -9140 is written once, at 0x44d815, in the full copy of -9160..-9148 into -9144..-9132 after NewPrintCent. -9172 has 133 writes / 41 reads, not 115/22.
  - 20 of the 21 "unmatched" GetString lines (4203..4716) are in that tail (0x44c498..0x44d7f3). The 21st (3568, string 0x150) matches the push 0x150 at 0x448354, which jumps into the shared call GetString at 0x448514.

1) This changes the brief's premises. The original RunAppraisal is 0x4453a0..0x44db06, i.e. 0x8766 bytes. #### notes
Method: I used windows and filtered greps of the original over [0x4453a0, 0x447c00) (2469 instructions, saved to scratchpad ra/r1.txt). I used anchors.txt plus exact our-C line numbers, checked against the WSL repo and agreeing with every anchor in R1, and ours.asm for our build's codegen.

Findings, in priority order:

(1) Behaviour bug, independent of matching. Each of the 5 two-bit switches (0x30/0xc0/0x300/0xc00/0x3000) pushes a different string id per case (case1/2/3 = base, base+1, base+2) before one shared GetString call. The anchor tool recorded only the case-1 id. Our C gives all three cases the case-1 id, so 10 ids are lost.

(2) Comparison signedness. All 35 page-overflow tests in R1 are signed (`cmp eax,0x1b5; jle`, 0 unsigned jumps). 33 of ours' 34 C tests are unsigned, through `(unsigned int)` casts or the unsigned uVar9; only 2458 is signed.

(3) The 5 selectors are C `switch` statements: a dec-eax chain with no intervening `test`, per docs/decomp-tips.md. Ours is an if/else-if chain that compiles to cmp 1/2/3.

(4) xbase is indented in place (+0x30 after the header, -0x30 at the end, restored from the header record on restart).

(5) Pass tests are written `value >= threshold` with the `if (pass) cnt++; else flags |= bit;` branch order. Ours writes `threshold <= value` and puts the flags branch first.

(6) Every first sub-item and every header new-page path is inline in the original. Ours uses `==0` wrappers and backward gotos; MSVC re-inverts at least the 0x4000 case.

(7) Restart targets. The 0xf header and the 0x4fff0 header overflow share the stub 0x44546c, which loops to 0x445422. The 0x4fff0 sub-items go to 0x4464b7 and then 0x445539. Each loop block has its own restart (0x446a1c, 0x446e59, 0x447290, 0x44770b, 0x447d21) and loop-test stub (0x446a3f, 0x446e7c, 0x4472b3, 0x44772e, 0x447d44). How the original C expresses the shared 0x44546c restart (goto vs nested loops) is unknown.

Evidence on slot sharing, relevant to the core frame task. In R1, slots -9100, -9112, -9124, -9128 and -9164 each hold 2-3 unrelated values:
- -9100: &rec.f2 (0x4454c8), then FUN_00444df0's result (0x4458e8), then the saved header recoff (0x446755).
- -9112: passtotal (0x445550, inc 0x4457c4), then the recoff (0x446747, +=0x4c at 0x44685a), then a field-address spill (0x44798a).
- -9124: the 0x4fff0 row pointer (0x445572), then subpass (0x446769, inc 0x4469dd).
- -9128: the pass flag, then field-address spills (0x447936, 0x447964), then the render-object pointer (0x447b36).
- -9164: the recoff, then field-address spills (0x44790e), then the render counter (0x447b2b, inc 0x447b78).
The address stores in the 0xe00000 header are never read back, and 0x4479d8/0x4479dc is a dead store pair. These slots therefore behave like shared spill/temp homes rather than single named variables. Ghidra's merged names (passtotal, tmp8, flatp, piVar10) follow that sharing.

In contrast, within R1:
- -9108 (total), -9116 (flags), -9120 (section start), -9104 (row pointer in the loop blocks), -9092/-9096 (accumulators) and -9168 (xbase) each have one role.
- -9144/-9136/-9132 and -9172 are write-only.
- Each overflow site writes -9144/-9136 twice (before and after the page-start test) and -9132 once (new-page path only).
- The rect top is always kept in edi and the row bottom in eax.

#### notes
1. reccmp compares only part of RunAppraisal. reccmp has no original size for the function, so it uses our size: reccmp/compare/functions.py sets orig_size = min(orig_max, recomp_size), and the db reports recomp_size 28728 = 0x7038 with orig_size None. `.orig_symbols.json` stores the same 0x7038, so frame.py and the anchors use it too.

The real original runs from 0x4453a0 to the `ret` at 0x44db05 (8085 instructions), with the 0xf jump table at 0x44db08 and padding to 0x44db20. The window is [0x4453a0, 0x44c3d8), 6667 instructions, which cuts the 0x7000 tail mid-instruction. So 1418 instructions are never compared: the 0x18000/0x260000/0x1080000/0xc00000 blocks, the finalize code, the display loop and LAB_0044d594.

Consequences:
- The 15.7%/19%/39% scores and the brief's slot counts are measured against a truncated original, and the window will grow as our function grows.
- -9140 is used (display-loop row y: 2 writes, 5 reads).
- -9144 is read once (0x44d987). -9136 is never read anywhere.
- The task's assumption that [0x44a400, 0x44d000) is "the rest" came from this truncation, so I covered up to 0x44db06.

2. Behaviour bugs in our C (not only codegen):
a) 0xf switch, rows 0x17d/0x188/0x191/0x19b: the row zeroes the next record's count and appends its id with its own, unzeroed count, on a stack array that is never initialised. This can write out of bounds (3880, 3929, 3978, 4051).
b) tmp8: the 0xf tail lacks `= 1` and the 0x70 tail does `= 1` instead of `++` (4056, 4965). If only flags&0xf comment rows exist, `if (tmp8 == 0) iVar13--` (4677) drops a real record.
c) The 0xf tail lacks `+0x18` (`iVar12 = iVar4`, asm `mov _iVar12$, iVar4` at 4054/4056). Every later page test based on iVar12 is 0x18 low until the next page break: the 0x70 cases' 2nd/3rd rows (e.g. 4865) and the 0x7000+ blocks (e.g. 4063, asm `iVar12+22`).
d) `SpeechLoadWavFile(wavbuf + 8)` (4817).
e) The InitAppraisalScreen argument is dropped (4681).
a-c look like the decompiler confusing the two merged switch tails at 0x44b6c6 and 0x44bebd. In R2 range, lines 3561-3593 and 2636-2650 may carry the wrong string ids (see extra_in_ours).

3. Register roles: esi is the record index and edi the row y throughout. ebp is the page start only up to 0x44ad38; after that it holds the record offset 0x4c*esi, and the page start lives in -9172 (reloaded into ebp at 0x44d574). In the display loop, ebp = &flat[n], edi = record pointer and esi = record count.

-9164 holds the record offset in the first part and the comment-row counter from 0x44add3. -9128 points to the next record's count: stored after every row in the second part, but only when a later row uses it in the first part. That looks like a spilled common-subexpression temp rather than a source variable.
